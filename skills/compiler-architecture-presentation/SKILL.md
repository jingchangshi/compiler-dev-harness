# Compiler Architecture Presentation

## Objective

Turn compiler implementation evidence into a presentation that explains both **how the code works** and **why the design is correct or risky**.

Default deliverable: a maintainable presentation project whose source of truth is:

- `slides.qmd` for content and layout;
- `styles.scss` for typography and visual system;
- `diagrams/*.excalidraw` for editable flow/architecture diagrams;
- `diagrams/*.svg` as the rendered/static diagram assets referenced by QMD;
- `_site/slides.html` as the Quarto Reveal.js build output when Quarto is available.

Do **not** hand-author the final HTML as the primary source unless the user explicitly asks for raw HTML.

Default audience: Chinese-speaking technical listeners comfortable with English identifiers, pass names, options, filenames, and IR/code.

## Non-negotiable presentation rules

1. **Chinese-first writing.**
   - Outside code/IR, write primarily in Chinese.
   - Preserve English for identifiers, pass options, API names, IR ops, filenames, and compact technical keywords.

2. **Short titles.**
   - Prefer titles such as `为什么要合并 VF？`, `Pass 在哪里执行？`, `核心流程`, `依赖模型`, `主要缺陷`, `改进建议`.
   - Keep titles to one line when possible; never put detailed reasoning in the title.

3. **Minimal cover.**
   - Use the component/pass name + a short keyword subtitle + optional compact metadata.
   - Avoid paragraphs and repeated explanations on the title slide.

4. **No visible generator provenance.**
   - Never show `generated by`, `created with`, `AI generated`, `... Skill`, or similar production metadata in visible slides.

5. **Readable browser presentation.**
   - Use Reveal.js through Quarto with `width: 1600`, `height: 900`.
   - Let Reveal.js scale the fixed logical canvas to the browser viewport.
   - Avoid responsive CSS that changes text wrapping unpredictably between browser sizes.

6. **Excalidraw-first diagrams.**
   - For pipelines, process flows, dependency maps, legality trees, and architecture diagrams, create editable `.excalidraw` source files first.
   - Export/update paired SVG files and reference those SVGs from QMD.
   - Keep diagram labels short and reserve extra width for CJK text.

## Workflow

### 1. Establish evidence

- For a repository/branch/commit/PR, read the actual code before drafting slides.
- For uploaded notes/design docs, use them as the requested evidence base; verify against source only when source access is available or requested.
- Capture exact file paths, pass names/options, key functions/classes, pipeline position, tests, known failure modes, and unsupported scenarios.
- Never invent source facts, test results, pipeline ordering, or IR.

### 2. Extract the architecture story

Identify:

- the optimization/correctness problem;
- pipeline position and representation before/after;
- the minimal before/after IR example;
- key analyses and data structures;
- legality guards and rewrite paths;
- corner cases versus design defects;
- prioritized improvements and validation strategy.

Separate observed implementation facts from reviewer inference.

### 3. Plan semantic slide roles

Use these roles as needed:

`hero`, `problem`, `pipeline`, `code-compare`, `algorithm`, `dependency-map`, `decision-tree`, `rewrite`, `evidence`, `risk-matrix`, `roadmap`, `summary`.

Use roughly 8-12 slides for a normal pass. Split content rather than shrinking code/diagram text.

### 4. Scaffold the Quarto project

Run:

```bash
python3 scripts/scaffold_quarto_project.py \
  --title '<PASS_OR_COMPONENT>' \
  --subtitle '目标 · Pipeline · IR · 合法性 · 缺陷' \
  --output <PROJECT_DIR>
```

Then replace the scaffold content with the actual presentation.

Read before composing:

- `references/compiler-presentation-guidelines.md`
- `references/quarto-reveal-style.md`
- `references/browser-display-and-excalidraw.md`
- `references/quarto-project-workflow.md`

### 5. Generate diagrams as editable assets

For pipeline/process/dependency/legality diagrams:

1. define the conceptual graph;
2. generate a valid `.excalidraw` source;
3. generate or export a paired `.svg`;
4. place both under `diagrams/`;
5. reference only the SVG from `slides.qmd`;
6. keep diagram details in nearby prose rather than overloading node labels.

Use `scripts/make_excalidraw_diagram.py` for deterministic source + same-geometry SVG fallback when a native Excalidraw exporter is unavailable.

### 6. Build and preview

Local author workflow:

```bash
make preview
```

or:

```bash
quarto preview slides.qmd
```

Final render:

```bash
make render
```

The bundled `_quarto.yml` configures Reveal.js at 1600x900 and uses `embed-resources: true`, so the final HTML can be a single distributable file.

If Quarto is unavailable in the current execution environment:

- still generate and validate the full source project;
- do not fabricate a Quarto-generated HTML;
- clearly state that `_site/slides.html` must be produced locally with `quarto render slides.qmd`.

### 7. Validate before delivery

Run the project checker:

```bash
python3 <PROJECT_DIR>/scripts/check_project.py
```

When Quarto is available, render the deck and visually inspect it in a browser.

Check:

- Chinese is the main prose language;
- titles are concise;
- cover is terse;
- no generator/skill attribution is visible;
- code is readable;
- diagrams fit the slide and labels fit their nodes;
- no horizontal/vertical overflow at common browser viewport sizes;
- final HTML is generated from QMD, not independently edited.

## Canonical narrative

Cover these concepts in this order unless the evidence genuinely lacks one:

1. `problem-background` — 问题 / 动机 / 优化目标
2. `pipeline-position` — pipeline 位置及前后 IR
3. `ir-before-after` — 最小 IR/code 前后对比
4. `core-algorithm` — 核心算法与关键数据结构
5. `dataflow-architecture` — 数据/依赖/移动边界
6. `corner-cases` — legality、拒绝条件、限制
7. `design-defects` — 假设、崩溃路径、覆盖缺口
8. `improvement-proposals` — P0/P1/P2 改进与验证

A title slide and final `总结` slide may wrap these sections.

## Visual system

Use Quarto Reveal.js as the baseline:

- white background;
- near-black text;
- Quarto-like blue accent;
- minimal decoration;
- light code blocks;
- shallow callouts;
- small border radii;
- no dark sandwich deck by default;
- no dashboard/KPI tile style;
- Chinese/English font stacks from `references/quarto-reveal-style.md`.

## Layout rules

- `hero`: pass/component name + short keyword subtitle.
- `problem`: concise claim + one mechanism figure.
- `pipeline`: horizontal pipeline diagram; highlight target pass.
- `code-compare`: aligned code columns with decisive lines highlighted.
- `algorithm`: numbered stages or one Excalidraw process diagram.
- `dependency-map`: diagram dominates; prose explains nuance.
- `decision-tree`: explicit `REJECT` branches.
- `rewrite`: compare rewrite variants in two columns.
- `evidence`: compact test/evidence ledger.
- `risk-matrix`: `问题 | 证据 | 后果 | 优先级` or add confidence when useful.
- `roadmap`: P0/P1/P2 columns.
- `summary`: at most three takeaways.

## Compiler-specific rules

### Pipeline

Show representation boundaries such as tensor -> memref, high-level dialect -> LLVM, host -> device, or scheduling -> codegen directly on the diagram.

### IR before/after

Use real reduced IR from source/tests when available. Mark simplified examples as `示意` or `schematic`. Show exactly what disappears, moves, fuses, becomes internal, or must be preserved.

### Algorithm

Explain phases first; function names/data structures are secondary annotations.

### Dataflow

Distinguish SSA, memory/alias, call/VF, control/region, and physical movement/synchronization. Never merge them into one unlabeled arrow type.

### Corner cases vs defects

- Corner case: deliberately handled/rejected by the design.
- Defect/risk: incomplete handling, brittle assumption, inconsistent behavior, missing coverage, crash path, or likely correctness/performance issue.

### Improvements

Use:

- `P0 正确性`
- `P1 稳健性 / 可维护性`
- `P2 优化 / 覆盖`

Each proposal should include a concrete change and a validation artifact or measurement.
